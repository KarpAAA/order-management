# Роудмап навчального проєкту: кроки 1–7

## Як користуватись

**Крок 0** робить Claude Code за `STEP-0-PROMPT.md`. Після нього в репо є:

- сервіс `api` з модулями identity, catalog, orders і окремим воркером;
- fake-psp, Postgres, Redis;
- Swagger і bull-board;
- `docs/requirements.md` — список вимог, з якого в кроці 1 пишуться тести.

Далі йдеш пункт за пунктом у порядку цього документа. Цикл на кожен пункт:

1. **Теорія** — розбираємо тему в сесії.
2. **Закласти** — додаємо це в систему. Можна сказати Claude Code: «закладаємо пункт 2.4 з docs/ROADMAP.md».
3. **Подивитись** — дивишся результат, який видно: графік, UI, зелений чи червоний тест, EXPLAIN.
4. **Записати** — коротко фіксуєш суть у конспекті в Notion.

**Чому такий порядок.** Спершу змінюємо саму систему: тести → бази → мікросервіси. Потім кладемо шари поверх готової системи: observability → Kubernetes → навантаження. AI — в кінці, окремим блоком.

Пункти з позначкою _(опційно)_ — якщо буде час і цікавість.

## Крок 1. Тестування

**Що змінюється.** У системі з'являються тести й CI. Сам код майже не змінюється, хіба виправляєш те, що знайдуть тести.

**Основа — твої конвенції:**

- fake-адаптери для портів, MSW для реальних HTTP-адаптерів
- Stryker на `domain/` і `application/`

Тести пишуться з `docs/requirements.md`.

**Теорія:** конспект → Testing.

- [x] **1.1 Стратегія: що на якому рівні тестуємо**
  - Закласти: пройтись по `docs/requirements.md` і біля кожної вимоги позначити рівень: unit, integration чи API. Налаштувати Vitest з окремими проєктами для unit і e2e.
  - Подивитись: розподіл вимог по рівнях. Побачиш «трофей» на своєму проєкті: більшість вимог лягає на API-рівень.

- [x] **1.2 Unit-тести доменної логіки**
  - Закласти: розрахунки (subtotal, знижки, податок, округлення) і стейт-машина. Для стейт-машини — усі дозволені й заборонені переходи, таблицею через `it.each`.
  - Подивитись: сотні тестів за частку секунди. Навмисно зміни правило округлення — подивись, які тести впали.

- [x] **1.3 Property-based тести (fast-check)**
  - Закласти: інваріанти розрахунку:

    - `subtotal = Σ lineTotal`

- [x] **1.4 Test doubles на use case-ах**

  - Подивитись: різницю між перевіркою стану (що лежить у fake-репозиторії) і перевіркою взаємодії (що подія опублікована).

- [x] **1.5 Тестові дані й ізоляція БД**

  - Подивитись: порівняй час прогону трьох стратегій: БД на файл, truncate між тестами, транзакція з відкатом. І подумай, чому відкат транзакції не працює, коли в тесті бере участь воркер.

- [x] **1.6 Інтеграційні тести з Testcontainers**
  - Закласти: репозиторії проти справжнього Postgres:
    - композитні ключі
    - унікальність SKU
    - optimistic locking: два паралельні оновлення одного замовлення, одне має впасти з конфліктом

- [x] **1.7 API / component тести**

- [x] **1.8 Ізоляція тенантів і ролі**

- [x] **1.9 Воркер і черги**

  - Подивитись: ретраї й failed jobs у bull-board під час прогону. І подумай, чому тут не можна «просто перевірити, що метод викликався».

  - Подивитись: імпортуй Prisma в `domain` — перевірка падає. Це страховка для кроку 3, коли модулі стануть сервісами.

  - Подивитись: зламана або забута міграція ловиться до мержу.

- [x] **1.15 CI (GitHub Actions)**
  - Закласти:
    - основний пайплайн: lint → typecheck → unit → integration/API (Testcontainers працюють у GitHub Actions) → міграції

## Крок 2. Бази даних і масштабування

**Що змінюється.** База й шар доступу до даних; API і домен майже не чіпаємо. Тести з кроку 1 працюють як страховка: після кожної зміни прогін показує, що нічого не зламалось.

**Нюанс:** режими мультитенантності 2 і 3 (пункти 2.5 і 2.6) краще робити на окремих гілках. Основна лінія лишається на спільних таблицях з RLS.

- [x] **2.1 Генератор даних**
  - Закласти: скрипт, що заливає, наприклад, 100 тенантів, 1–2 млн замовлень і 5–10 млн подій. Розподіл реалістичний: кілька «великих» тенантів і багато дрібних.
  - Подивитись: розміри таблиць та індексів (`pg_total_relation_size`). Це база для всіх експериментів далі.

- [x] **2.2 Індекси й EXPLAIN**
  - Закласти: розібрати основні запити через `EXPLAIN (ANALYZE, BUFFERS)`: список замовлень тенанта за статусом з курсорною пагінацією, історія подій. Підібрати композитні індекси.
  - Подивитись: Seq Scan → Index Scan, час і кількість прочитаних сторінок до й після. І чому OFFSET-пагінація деградує, а курсорна ні.

- [ ] **2.3 Партиціювання `order_events`**
  - Закласти:
    - range-партиції за місяцями по `created_at` (ключ уже підготовлений у кроці 0)
    - автоматичне створення наступних партицій: pg_partman або BullMQ repeatable job
    - retention: старі партиції видаляються
  - Подивитись: partition pruning в EXPLAIN. І `DROP` партиції замість `DELETE` мільйонів рядків — миттєво й без роздування таблиці.

- [ ] **2.4 Мультитенантність, режим 1: RLS**
  - Закласти:
    - політики Row-Level Security на всіх tenant-таблицях
    - на кожну транзакцію `set_config('app.workspace_id', …, true)` з tenant context — та сама «єдина точка», закладена в кроці 0
    - застосунок ходить у БД користувачем, який не є власником таблиць
  - Подивитись: прибери фільтр workspace з репозиторію — тести ізоляції з 1.8 усе одно зелені, бо захищає вже сама база.

- [ ] **2.5 Мультитенантність, режим 2: схема на тенанта**
  - Закласти: перемикач стратегії через конфіг, `search_path` для кожного тенанта, накат міграцій на N схем.
  - Подивитись: створи 1000 тенантів. Як ростуть час міграцій і розмір каталогу Postgres, як поводиться пул з'єднань.

- [ ] **2.6 Мультитенантність, режим 3: БД на тенанта** _(опційно)_
  - Закласти: маршрутизація підключень за тенантом, пул клієнтів з лімітом.
  - Подивитись: скільки з'єднань відкривається і де межа. Зведи три режими в таблицю в docs: ізоляція, вартість, складність міграцій, скільки тенантів тягне.

- [ ] **2.7 PgBouncer**
  - Закласти: PgBouncer у transaction mode між застосунком і Postgres, плюс налаштування Prisma під нього.
  - Подивитись: 500 клієнтських з'єднань перетворюються на 20 серверних. І що ламається в transaction mode: сесійні `SET`. Саме тому в 2.4 потрібен `is_local = true`.

- [ ] **2.8 Репліка для читань**
  - Закласти: streaming-репліка Postgres у docker compose. Списки читаються з репліки, записи йдуть у primary.
  - Подивитись: затримку реплікації — створив замовлення й одразу не бачиш його у списку (read-your-writes). Варіанти рішення: читати свої записи з primary N секунд або за LSN.

- [ ] **2.9 Кеш у Redis**
  - Закласти: cache-aside для каталогу продуктів з інвалідацією при зміні. Захист від cache stampede: lock / single-flight або TTL з jitter.
  - Подивитись: hit ratio і латентність до й після. Експеримент: 200 паралельних запитів при порожньому кеші — скільки з них дійде до БД без захисту і з ним.

- [ ] **2.10 Rate limiting на тенанта**
  - Закласти: token bucket у Redis за workspace (і за користувачем), 429 з `Retry-After`. Ліміти залежать від тенанта.
  - Подивитись: «шумний сусід» — один тенант упирається в ліміт, решта працює як звичайно.

- [ ] **2.11 Шардинг (Citus)**
  - Закласти:
    - Citus у docker compose: coordinator + 2 workers
    - tenant-таблиці розподілені за `workspace_id` і co-located
    - `users` і `workspaces` — reference tables

    Композитні ключі з кроку 0 дають зробити це без переписування схеми.

  - Подивитись:
    - запит у межах одного тенанта йде на один шард, а «мої workspaces» чи звіт по всіх тенантах — на всі (видно в EXPLAIN)
    - додай третій worker і зроби rebalance шардів

- [ ] **2.12 Міграції без даунтайму (expand/contract)**
  - Закласти: реальна зміна схеми в кілька кроків, наприклад NOT NULL-колонка з backfill батчами: expand → код пише в обидва місця → backfill → код читає нове → contract.
  - Подивитись: стара й нова версії застосунку працюють одночасно на одній схемі. Прогін під навантаженням — у кроці 6.

**Результат кроку:** ти бачив на своїх даних, як працюють індекси, партиції, три режими мультитенантності, пул, репліка, кеш і шардинг.

## Крок 3. Мікросервіси й брокери

**Що змінюється.** З модульного моноліту виділяються сервіси, з'являються RabbitMQ і Kafka. Межі модулів, які перевіряли architecture tests з 1.13, стають межами сервісів.

- [ ] **3.1 Контракти повідомлень**
  - Закласти: `packages/contracts` — схеми команд і подій (zod або JSON Schema) з версією, спільні для продюсерів і консюмерів.
  - Подивитись: одне джерело правди для всіх сервісів. Що буде, якщо змінити поле без нової версії, покаже 3.12.

- [ ] **3.2 RabbitMQ і payments-service**
  - Закласти: payments-service з власною БД, логіка PSP переїжджає туди з `api`. Команда `ChargePayment` іде через RabbitMQ, відповідь — `PaymentSucceeded` або `PaymentFailed`.
  - Подивитись: RabbitMQ Management UI — exchanges, черги, повідомлення в дорозі.

- [ ] **3.3 RabbitMQ глибше**
  - Закласти: ack/nack, prefetch, ретраї з затримкою (TTL + dead-letter exchange), DLQ, обробка «отруйних» повідомлень.
  - Подивитись:
    - вбий консюмера посеред обробки — повідомлення повертається в чергу
    - «отруйне» повідомлення після N спроб потрапляє в DLQ

- [ ] **3.4 Outbox**
  - Закласти: закриваємо «known gap» з кроку 0. Подія пишеться в outbox у тій самій транзакції, relay публікує її в брокер (`SELECT … FOR UPDATE SKIP LOCKED`). За конвенціями це `reliable`-події.
  - Подивитись: вбий брокер між commit і публікацією — подія не губиться й доходить, коли брокер піднімається.

- [ ] **3.5 Ідемпотентні консюмери**
  - Закласти: inbox — таблиця оброблених повідомлень у кожному консюмері.
  - Подивитись: відправ те саме повідомлення 5 разів — ефект буде один.

- [ ] **3.6 inventory-service**
  - Закласти: запаси й резервації (reserve / release) з власною БД. Команди `ReserveStock` і `ReleaseStock` через RabbitMQ.
  - Подивитись: конкурентні резервації останньої одиниці товару — хто виграє і чому (блокування чи optimistic locking).

- [ ] **3.7 Сага (оркестрація в `api`)**
  - Закласти:
    - кроки: place → reserve stock → charge → confirm
    - компенсації: оплата не пройшла → release stock
    - стан саги зберігається в БД, у кроків є таймаути (BullMQ delayed job)
    - тут же з'являється скасування `PENDING_PAYMENT`, заборонене в кроці 0
  - Подивитись: сценарії success, declined, out of stock і «payments лежить» — статуси й компенсації в історії замовлення.

- [ ] **3.8 Kafka**
  - Закласти: доменні події (`OrderPlaced`, `OrderPaid`, `OrderCancelled`, `OrderFulfilled`, `PaymentSucceeded`) з outbox у топіки. Ключ повідомлення — `orderId`, щоб зберігався порядок подій одного замовлення. Плюс Kafka UI.
  - Подивитись: партиції, offsets, consumer lag. Чому з ключем порядок зберігається, а без нього ні.

- [ ] **3.9 analytics-service**
  - Закласти: консюмер Kafka будує агрегати у власній БД — read model у стилі CQRS: виручка тенанта за день, кількість замовлень за статусами.
  - Подивитись:
    - вимкни analytics на 10 хвилин, увімкни — він доганяє (lag → 0)
    - перебудуй read model з нуля через replay від початку топіка

- [ ] **3.10 notifications-service**
  - Закласти: листи на події замовлення через Mailpit (фейковий SMTP з вебінтерфейсом), без дублів при повторній доставці.
  - Подивитись: листи в UI Mailpit. І що було б із дублями без 3.5.

- [ ] **3.11 Стійкість викликів**
  - Закласти: у виклику payments → fake-psp: таймаути, ретраї з backoff + jitter, circuit breaker.
  - Подивитись: fake-psp з 50% помилок — breaker відкривається, система деградує контрольовано, а не висне. Що в цей момент бачить користувач.

- [ ] **3.12 Contract testing**
  - Закласти: у CI продюсери й консюмери перевіряються проти `packages/contracts`. Pact — якщо з'явиться синхронний HTTP між сервісами.
  - Подивитись: зміни поле в події — CI падає ще до деплою.

- [ ] **3.13 E2E / system тести**
  - Закласти: docker compose з усіма сервісами і 3–4 наскрізні сценарії: успіх, відмова оплати, нема на складі, скасування.
  - Подивитись: повний шлях через обидва брокери. І скільки часу займає такий тест.

- [ ] **3.14 CDC через Debezium** _(опційно)_
  - Закласти: замість власного relay з 3.4 — Debezium читає outbox-таблицю з WAL і пише в Kafka.
  - Подивитись: порівняння з власним relay — затримка, навантаження на БД, складність.

**Результат кроку:** система з п'яти сервісів, де команди йдуть через RabbitMQ, події через Kafka, а замовлення проходить сагою з компенсаціями.

## Крок 4. Observability

**Що змінюється.** Бізнес-логіку не чіпаємо. Додаються інструментація і стек, щоб бачити, що відбувається в системі з кількох сервісів і брокерів.

- [ ] **4.1 Структуровані логи**
  - Закласти:
    - pino (JSON), рівні логування
    - redaction секретів і персональних даних
    - correlation id: створюється на вході (або береться з заголовка) і прокидається в BullMQ-job-и та заголовки повідомлень RabbitMQ і Kafka
  - Подивитись: усі логи одного запиту в усіх сервісах за одним id.

- [ ] **4.2 Grafana-стек**
  - Закласти: `grafana/otel-lgtm` у docker compose — Grafana, Loki, Tempo, Prometheus і OTel Collector в одному контейнері.
  - Подивитись: Grafana UI і джерела даних.

- [ ] **4.3 Трейси (OpenTelemetry)**
  - Закласти:
    - автоінструментація: HTTP, NestJS, Postgres, Redis, RabbitMQ, Kafka
    - ручні span-и для кроків саги
    - передача контексту через заголовки повідомлень і дані BullMQ-job-ів
  - Подивитись: один трейс від place через сагу, payments і inventory до analytics — waterfall у Tempo. Де саме йде час.

- [ ] **4.4 Логи ↔ трейси**
  - Закласти: traceId у кожному лозі, зв'язка Loki → Tempo в Grafana.
  - Подивитись: знайшов помилку в логах — один клік, і перед тобою трейс цього запиту.

- [ ] **4.5 Метрики**
  - Закласти:
    - RED для HTTP: rate, errors, гістограма тривалості
    - глибина черг RabbitMQ і BullMQ, consumer lag Kafka
    - пул з'єднань і Postgres
    - бізнес-метрики: placed / paid

    Окремо розберися з кардинальністю: чому не можна вішати мітку `workspace_id` на кожну метрику, коли тенантів тисячі.

  - Подивитись: власний дашборд системи.

- [ ] **4.6 SLO і алерти**
  - Закласти: SLI (частка успішних place, p95 латентності), SLO і правила алертів у Grafana.
  - Подивитись: поклади fake-psp — алерт спрацював. Підніми — погас.

- [ ] **4.7 Error tracking** _(опційно)_
  - Закласти: Sentry або self-hosted GlitchTip з прив'язкою до трейсів.
  - Подивитись: згруповані помилки з контекстом запиту.

**Результат кроку:** будь-яку проблему можна пройти від алерту до метрики, від метрики до трейсу, від трейсу до логу.

## Крок 5. Kubernetes

**Що змінюється.** Система переїжджає з docker compose у локальний кластер. У самому застосунку додаються тільки health-ендпоінти й коректне завершення роботи.

- [ ] **5.1 Кластер**
  - Закласти: kind на 3–4 вузли (або k3d), плюс k9s чи Lens для візуалу.
  - Подивитись: вузли, системні pod-и, як kubectl спілкується з API server.

- [ ] **5.2 Маніфести сервісів**
  - Закласти:
    - образи в локальному реєстрі
    - Deployment + Service для кожного сервісу; воркери — окремим Deployment з того самого образу, з іншим entrypoint
    - ConfigMap і Secret, requests / limits
    - Kustomize: base + overlays
  - Подивитись: `kubectl apply` — і все піднялось. Далі `describe pod`, events, логи.

- [ ] **5.3 Probes і graceful shutdown**
  - Закласти:
    - liveness і readiness (terminus: перевіряє БД, Redis, брокери)
    - `enableShutdownHooks`: дочекатися поточних HTTP-запитів, job-ів і повідомлень
    - `preStop`
  - Подивитись: rolling update під curl-циклом — нуль помилок. Потім вимкни graceful shutdown, повтори — з'являються помилки.

- [ ] **5.4 Вхідний трафік**
  - Закласти: Gateway API через Envoy Gateway або Traefik (ingress-nginx уже знятий з підтримки). Service типу LoadBalancer — через cloud-provider-kind або MetalLB.
  - Подивитись: шлях запиту ззовні: Gateway → Service → pod, і як він розподіляється між репліками.

- [ ] **5.5 Stateful-компоненти**
  - Закласти:
    - CloudNativePG: primary + 2 репліки, автоматичний failover
    - Redis
    - RabbitMQ через cluster operator
    - Kafka через Strimzi, у режимі KRaft

    Citus лишається в compose-експериментах кроку 2.

  - Подивитись: вбий primary-pod — CNPG промоутить репліку. Скільки помилок бачить застосунок.

- [ ] **5.6 Автоскейлінг**
  - Закласти: metrics-server + HPA для `api` за CPU. KEDA для воркерів і консюмерів — за довжиною черги й consumer lag.
  - Подивитись: під навантаженням додаються pod-и. Черга росте — KEDA додає консюмерів, спадає — прибирає.

- [ ] **5.7 Розміщення по вузлах і «регіонах»**
  - Закласти: мітки вузлів (zone = eu / us), `topologySpreadConstraints`, anti-affinity.
  - Подивитись: вимкни вузол — pod-и переїхали на інші. Репліки одного сервісу не сидять на одному вузлі.

- [ ] **5.8 Observability в кластері**
  - Закласти: OTel Collector і Grafana-стек з кроку 4 — у кластері, логи збираються зі stdout pod-ів.
  - Подивитись: ті самі дашборди, але з метаданими pod і node.

- [ ] **5.9 Smoke-тести після деплою**
  - Закласти: Job після rollout, що робить кілька ключових запитів. Якщо вони провалюються — rollback.
  - Подивитись: «поганий» реліз автоматично відкочується.

- [ ] **5.10 GitOps** _(опційно)_
  - Закласти: ArgoCD — стан кластера синхронізується з git.
  - Подивитись: змінив маніфест у репо — кластер оновився сам.

- [ ] **5.11 Canary** _(опційно)_
  - Закласти: Argo Rollouts — нова версія отримує 10% трафіку, метрики аналізуються, при проблемах відкат автоматичний.
  - Подивитись: версія з навмисним баґом не доходить до 100%.

**Результат кроку:** уся система живе в кластері, сама масштабується, переживає падіння pod-ів і вузлів, оновлюється без даунтайму.

## Крок 6. Навантаження й chaos

**Що змінюється.** Код не змінюється, хіба виправляєш знайдене. Додаються k6-сценарії й chaos-експерименти; усе дивишся в Grafana з кроку 4.

Абсолютні цифри на одній машині нереалістичні, але відносні ефекти — справжні.

- [ ] **6.1 k6 і реалістичний профіль**
  - Закласти: сценарії з багатьма тенантами й користувачами: 70% перегляд каталогу, 20% створення замовлень, 10% place. Результати k6 йдуть у Prometheus → Grafana, поруч з метриками системи.
  - Подивитись: навантаження й реакцію системи на одному дашборді.

- [ ] **6.2 Load**
  - Закласти: очікуване навантаження протягом 15–30 хвилин.
  - Подивитись: чи виконуються SLO з 4.6.

- [ ] **6.3 Stress / breakpoint**
  - Закласти: нарощування навантаження до падіння.
  - Подивитись: що ламається першим — CPU api, пул з'єднань, Postgres чи черги. Виправ, повтори й подивись, як вузьке місце «переїжджає».

- [ ] **6.4 Spike**
  - Закласти: стрибок навантаження ×10 за кілька секунд.
  - Подивитись: як швидко реагують HPA і KEDA, що відбувається з чергами й 429.

- [ ] **6.5 Soak**
  - Закласти: помірне навантаження протягом кількох годин.
  - Подивитись: пам'ять, з'єднання, ріст черг і партицій.

- [ ] **6.6 Шумний сусід**
  - Закласти: один тенант генерує 80% трафіку.
  - Подивитись: вплив на інших тенантів без rate limiting з 2.10 і з ним.

- [ ] **6.7 Chaos Mesh**
  - Закласти:
    - PodChaos: вбити api, воркер, консюмер
    - NetworkChaos: затримка 80 мс між «регіонами», втрати пакетів до PSP
    - вбити брокер
  - Подивитись: чи відновлюється система — ретраї, breaker, outbox, сага. І що в цей час бачить клієнт.

- [ ] **6.8 Failover під навантаженням**
  - Закласти: вбити primary CNPG під час k6-прогону.
  - Подивитись: скільки запитів упало і скільки тривало відновлення.

- [ ] **6.9 Реплікація під навантаженням**
  - Закласти: інтенсивний запис плюс читання з реплік.
  - Подивитись: lag реплікації і що він робить з read-your-writes.

- [ ] **6.10 Деплой і міграція під навантаженням**
  - Закласти: rolling update і expand/contract-міграція з 2.12 під k6.
  - Подивитись: нуль помилок — або де саме вони з'являються.

**Результат кроку:** ти знаєш межі своєї системи, її вузькі місця і як вона поводиться при відмовах.

## Крок 7. AI

**Що змінюється.** Поверх готової системи додається AI-функціональність окремим модулем. Основна система від AI не залежить.

- [ ] **7.1 Ембединги й pgvector**
  - Закласти: ембединги описів продуктів (локально через Ollama або через API) і семантичний пошук по каталогу з ізоляцією тенантів.
  - Подивитись: запит «щось для бігу» знаходить кросівки, хоча слова «біг» в описі немає.

- [ ] **7.2 Гібридний пошук і reranking**
  - Закласти: full-text Postgres + вектори, злиття результатів (RRF), reranker.
  - Подивитись: якість на наборі запитів у трьох варіантах: тільки вектори, гібрид, гібрид + reranking.

- [ ] **7.3 Асистент з tool calling**
  - Закласти: асистент тенанта, чиї інструменти працюють поверх наявних use case-ів: знайти замовлення, показати статус, створити чернетку, скасувати. Перевірки ролей ті самі, що в API. Дії, що змінюють дані, — тільки після підтвердження людиною.
  - Подивитись: діалог і виклики інструментів у трейсі з кроку 4.

- [ ] **7.4 MCP-сервер**
  - Закласти: ті самі інструменти як MCP-сервер.
  - Подивитись: Claude Desktop або Claude Code керує замовленнями твого тенанта.

- [ ] **7.5 Evals**
  - Закласти: набір запитів з очікуваними результатами: recall@k для пошуку, правильність вибору інструменту, LLM-as-judge для відповідей.
  - Подивитись: змінив промпт чи модель — як змінились метрики.

- [ ] **7.6 Продакшн-аспекти**
  - Закласти:
    - стрімінг відповіді через SSE
    - довгі задачі через чергу
    - облік токенів і вартості по тенантах
    - захист від prompt injection: дані тенанта — недовірений вхід
    - окремий rate limit на AI
  - Подивитись: вартість AI по тенантах на дашборді.

**Результат кроку:** AI-функції поверх реальної мультитенантної системи — з ізоляцією, трейсами, оцінкою якості й контролем вартості.
