# 3.13 An order through four services: how long a system test takes, and where the time goes

Since 3.13 the whole system is run by a test: the four services from their images in the
compose project `oms-system`, and four scenarios through the HTTP API (`devtools/system`,
ADR 0022). This is what such a run costs, next to the suites that test each service to its
boundary. Decision and rejected alternatives: ADR 0022.

Reproduce: `pnpm test:system`. It prints the start of the stack, the time of every scenario
and, for the first one, the time from `place` to `PAID` and to the mails.

One laptop (8 cores, Docker Desktop on Windows), the dev stack running beside it. Five green
runs; the numbers move by a second from run to run, because every relay looks once a second
and nobody chooses where in that second a message is written.

## A. The run

| Part                                          | Time              |
| --------------------------------------------- | ----------------- |
| images built again (a changed lockfile)       | 523 s, then 341 s |
| images cached: volumes removed, containers up | 42 s to 83 s      |
| … until every queue has its consumer          | 10 s to 20 s more |
| the four scenarios                            | 20 s to 22 s      |
| **`pnpm test:system`, images cached**         | **76 s to 124 s** |

The removal of the stack afterwards is not in the last row: vitest stops its clock before it.

Three quarters of a warm run is the stack: fifteen containers, of which the replica copies
the primary before it answers, four one-shot migrations and two seeds wait for their
databases, and five Node processes boot. The scenarios are a fifth of it.

The first run after a change of the lockfile or of the root `package.json` rebuilds the
dependency layer of all four images: both files are copied before `pnpm install` in every
Dockerfile. The two runs after `test:system` was added to the root scripts are the first
row: nine minutes, then six, before the cache held.

## B. The scenarios

| Scenario                                         | Time           | What it waits for                                                               |
| ------------------------------------------------ | -------------- | ------------------------------------------------------------------------------- |
| paid                                             | 4.1 s to 4.9 s | `PAID`, then two mails                                                          |
| declined, the stock released, placed again, paid | 6.3 s to 7.6 s | `PAYMENT_FAILED`, `STOCK_RELEASED` in the history, `PAID`, then four mails      |
| out of stock                                     | 2.0 s to 2.2 s | `DRAFT`, then two mails: one answer of inventory, payments is never asked       |
| cancelled while the charge is under way          | 7.7 s to 7.9 s | a call at the provider, 202, `CANCELLED`, the void, `STOCK_RELEASED`, two mails |

The cancellation is as long as the provider is slow: the charge it interrupts takes 5 s to
7.5 s by the setting of the scenario, and the void can only follow it.

## C. One paid order

| From `place` to …     | Five runs                         |
| --------------------- | --------------------------------- |
| `PAID` seen by a GET  | 2.3 s, 2.7 s, 2.8 s, 3.2 s, 3.4 s |
| both mails in Mailpit | 3.7 s, 3.8 s, 4.3 s, 4.7 s        |

Where it goes. A message between two services waits in an outbox until the relay of its
service looks (`OUTBOX_POLL_INTERVAL_MS=1000`): between 0 and 1 s, half a second on average.
A paid order crosses four of them:

```
place ─ api outbox ─▶ inventory ─ outbox ─▶ api ─ outbox ─▶ payments ─ PSP 0.2–0.3 s ─ outbox ─▶ api: PAID
        0…1 s                    0…1 s            0…1 s                                 0…1 s
```

Four waits of half a second and a provider of a quarter: 2.3 s expected, between 0.3 s and
4.3 s possible, and the five runs sit around it. The work itself (the transactions, four
messages through the broker, PgBouncer, a GET that may be served by the replica) is not
visible at this scale.

The mail adds one relay more (the event `orders.order-paid` leaves through the outbox of
the api) and the dispatcher of notifications, which also looks once a second: about a second
after `PAID`.

So the latency of an order is the polling of the relays, not the services. It is a setting:
the e2e suites run the same code with 50 ms. Nothing was changed for the test (ADR 0022);
a relay that does not poll is roadmap 3.14 (CDC), second pass.

## D. Next to the suites of the services

`pnpm test:e2e`, the same machine, the same day:

| Suite                           | Tests   | Time              |
| ------------------------------- | ------- | ----------------- |
| api (33 files)                  | 519     | 76 s              |
| inventory                       | 33      | 16 s              |
| notifications                   | 22      | 18 s              |
| payments                        | 41      | 23 s              |
| **all four, one after another** | **615** | **141 s**         |
| **system**                      | **4**   | **76 s to 124 s** |

A test of a service costs a quarter of a second of the run; a scenario of the system twenty
to thirty, with its share of the stack. And the 615 include what no scenario can do: a
message delivered twice, an answer for an old attempt, a step that times out, two orders for
the last unit at the same moment. That is the whole argument for four scenarios and not
forty.

## E. A broken link

What the suite is for. Each change made in `docker-compose.system.yml`, run once, reverted.

| Change                                                 | Result                               | First red after | What explains it                                                                                                          |
| ------------------------------------------------------ | ------------------------------------ | --------------- | ------------------------------------------------------------------------------------------------------------------------- |
| payments: `PSP_BASE_URL` to a host that is not there   | 3 red, out of stock green            | 30 s            | `stack.log`, payments: `psp charge call=1 status=none`, `payments.commands: delivery 1 of 4 failed, again in 30000 ms`    |
| notifications: `SMTP_HOST` to a host that is not there | 4 red, every order ends as it should | 30 s            | nothing in `stack.log`: a try to send that fails is not logged until the notification is given up (ADR 0022 → Known gaps) |

Every suite of every service is green with either change in place.

One more was met on the way, not made on purpose: on the first run the api and the provider
did not answer on their host ports for two minutes while they answered inside their
containers, and a request of a later run hung for 30 s and was reset. Both went away with
`127.0.0.1` in place of `localhost` (Docker Desktop on Windows, the IPv6 side of a published
port). A system test also tests the machine it runs on.
