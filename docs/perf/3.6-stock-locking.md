# 3.6 Who gets the last unit

Many orders want the same stock at the same moment. This is what four ways of writing
"reserve one unit" do with that, measured on one row. Decision and rejected alternatives:
ADR 0016.

Reproduce: `pnpm db:explain:stock` (`services/inventory/prisma/explain/locking.ts`), after
`pnpm infra:up`. It creates a table of its own in the database of inventory-service
(`stock_locking_demo`: `on_hand`, `reserved`, `version`), runs the scenarios and drops the
table; the tables of the service are not touched. Every buyer has a connection of its own and
all of them start together. Postgres 18 in Docker on one laptop, default `READ COMMITTED`; the
numbers are one run, and the counts of the `naive` rows differ from run to run.

## The four ways

```sql
-- naive: read, check in the code, write the number that was read plus one
BEGIN;
SELECT on_hand, reserved FROM stock WHERE id = 1;       -- everybody reads reserved = 0
UPDATE stock SET reserved = 1 WHERE id = 1;             -- and everybody writes 1
COMMIT;

-- conditional: the check and the write are one statement
UPDATE stock SET reserved = reserved + 1 WHERE id = 1 AND on_hand - reserved >= 1;

-- for update: lock the row, then read, check in the code, write
BEGIN;
SELECT on_hand, reserved FROM stock WHERE id = 1 FOR UPDATE;   -- the second buyer waits here
UPDATE stock SET reserved = 1 WHERE id = 1;
COMMIT;

-- version: nobody waits; write only if nobody wrote since the read, otherwise read again
SELECT on_hand, reserved, version FROM stock WHERE id = 1;
UPDATE stock SET reserved = 1, version = version + 1 WHERE id = 1 AND version = 0;  -- 0 rows: retry
```

## A. 50 buyers, 1 unit

| Strategy    | Told "yours" | Held in the row | Statements | Retries | Time  |
| ----------- | -----------: | --------------: | ---------: | ------: | ----- |
| naive       |       **18** |               1 |        168 |       0 | 36 ms |
| conditional |            1 |               1 |         50 |       0 | 34 ms |
| for update  |            1 |               1 |        151 |       0 | 60 ms |
| version     |            1 |               1 |        149 |      49 | 46 ms |

`naive` sold the last unit to 18 buyers, and the row says one is held: a lost update. No error
was raised anywhere, and a `CHECK (reserved <= on_hand)` would not have raised one either,
since `1 <= 1`. The transaction around the two statements changed nothing: at `READ COMMITTED`
a transaction does not stop another one from reading the same row.

The other three are correct, and they answer "who wins" differently:

- **conditional** and **for update**: whoever takes the lock of the row first. The others wait
  for that transaction to end; Postgres then gives them the row as it is now, and they see
  that nothing is free.
- **version**: whoever commits its write first. The others are not made to wait; they are
  told that the row changed, read it again and see that nothing is free. 49 retries for 49
  losers: with one unit a loser retries once.

## B. 50 buyers, 25 units

| Strategy    | Told "yours" | Held in the row | Statements | Retries | Time   |
| ----------- | -----------: | --------------: | ---------: | ------: | ------ |
| naive       |       **50** |           **1** |        200 |       0 | 72 ms  |
| conditional |           25 |              25 |         50 |       0 | 39 ms  |
| for update  |           25 |              25 |        175 |       0 | 89 ms  |
| version     |           25 |              25 |        755 |     340 | 242 ms |

This is where the optimistic lock shows what it costs on a row that is fought over. Only one
buyer can win a round; every other buyer who still sees stock tries again. 340 retries and
755 statements for the 175 that the pessimistic lock needed, and three times the time. The
work grows with the square of the contention, and all of it is wasted work that the database
did and threw away.

The same lock is the right one for an order (`orders.version` in the api): two people rarely
edit one order at the same moment, a conflict is shown to a person as `409`, and nobody ever
waits for a lock held by a slow client. Optimistic when a conflict is the exception,
pessimistic when it is the normal case.

## C. Two rows, two orders

20 orders, each locks two rows one after the other. Half of them name the rows `1, 2`, the
other half `2, 1`.

| Rows are locked               | Done | Broken by the database | Time    |
| ----------------------------- | ---: | ---------------------: | ------- |
| in the order each order names |    1 |                 **19** | 3058 ms |
| in one order for everybody    |   20 |                      0 | 1078 ms |

An order that holds row 1 and waits for row 2, and another that holds row 2 and waits for
row 1, wait for each other forever. Postgres notices after `deadlock_timeout` (1 s) and ends
one of them with `40P01`. Locking in one order for everybody removes the cycle: everyone who
wants both rows queues at the first one.

## What the service does

- **Stock: `SELECT … ORDER BY product_id FOR UPDATE`** (`StockRepository.lockMany`), for all
  the products of a command in one statement, before anything is read or decided. The rule
  "no more is held than is free" lives in `StockItem.reserve()`, which needs the levels in
  memory, so the row must stay locked from the read to the write. The conditional `UPDATE` is
  the cheapest of the four (one statement, table A and B), but it puts the rule into SQL: with
  it there is no domain object to hold the rule. That trade is recorded in ADR 0016.
- **A reservation: `version`** (`ReservationsRepository.save`). Two releases of one
  reservation are rare; the one that loses is rolled back and delivered again.
- **`CHECK (reserved <= on_hand)`** on `stock_items`: the last line. It does not catch a lost
  update (table A), it catches a bug that would hold more than there is.

The same race against the real service, with four replicas and the broker in between:
`services/inventory/test/inventory/concurrency.e2e-spec.ts` (INV-060 … INV-067). With the
`FOR UPDATE` removed from `lockMany`, INV-060 fails with four orders holding the one unit.
