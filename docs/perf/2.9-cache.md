# 2.9 Catalog cache in Redis

Data: `pnpm db:datagen` (full), the same database as 2.2–2.8: 100 tenants, 22 040 products,
4 695 of them in the biggest tenant. Postgres 18 behind PgBouncer (20 server connections),
Redis 7, all in Docker on one machine. Decision and rejected alternatives: ADR 0010.

Reproduce: `pnpm db:explain:cache` (`services/api/prisma/explain/cache.ts`). It runs the
`RedisCache` of the application against the dev Redis under its own key prefix, deletes its
keys at the end and writes no table. "Database" below is what `CatalogQueryService` sends for
one read: the tenant frame of 2.4 around the query (`BEGIN; set_config; query; COMMIT`) plus
the workspace terms, as the application role through PgBouncer. The numbers are one run on a
laptop, one caller at a time except in C.

## A. One read

1000 rounds each.

|         |           | p50     | p95     |
| ------- | --------- | ------- | ------- |
| product | database  | 2.33 ms | 3.45 ms |
| product | cache hit | 0.56 ms | 0.98 ms |
| list    | database  | 2.27 ms | 3.31 ms |
| list    | cache hit | 0.68 ms | 1.18 ms |

A hit is two Redis `GET`s (the version of the workspace, then the value) and a `JSON.parse`;
the database read is five round trips.

## B. Hit ratio

10 000 product reads over the 4 695 products of one tenant, skewed (Zipf: the product of rank
_r_ is read with probability ∝ 1/_r_), starting from an empty cache. A catalog change
invalidates the whole workspace.

| Catalog changes     | Hit ratio | Database reads | p50     | p95      |
| ------------------- | --------- | -------------- | ------- | -------- |
| none                | 77.9 %    | 2 213          | 0.65 ms | 5.79 ms  |
| one per 2 000 reads | 61.9 %    | 3 811          | 1.01 ms | 7.16 ms  |
| one per 500 reads   | 45.9 %    | 5 408          | 4.16 ms | 10.19 ms |
| one per 100 reads   | 28.6 %    | 7 143          | 4.09 ms | 6.46 ms  |

Without the cache every row would be 10 000 database reads at about 2.3 ms.

Redis' own counters over the whole run (`INFO stats`): `keyspace_hits` +70 406,
`keyspace_misses` +54 957. They count commands, not reads of the application: a hit is two
`GET`s, and the first read of a workspace misses on the version key too. The hit ratio above
comes from `RedisCache.stats()`.

## C. Cache stampede

200 callers read one empty key at the same moment, from 4 processes (4 `RedisCache`s, each
with its own connection and its own in-flight map).

| Protection                 | Database reads | All 200 answered in |
| -------------------------- | -------------- | ------------------- |
| none                       | 200            | 348 ms              |
| single-flight              | 4              | 19 ms               |
| single-flight + Redis lock | 1              | 63 ms               |

## D. TTL jitter

1000 keys stored in the same second with a TTL of 300 s ±10 %: they expire between 270 s and
330 s from then, and the busiest second takes 25 of them. Without jitter it takes all 1000.

## E. The cache and the replica

Not a number but a case, kept as a test (CCH-006, `test/replica/read-replica.e2e-spec.ts`):
the replica is frozen, an admin changes a price, a colleague reads the product. With the fill
left on the request's read source the colleague got **1000** (the old price, from the
replica), and it was stored for the TTL. With the fill on the primary they get 2500, while
their orders list in the same test still comes from the frozen replica.

## Findings

1. **A hit is four times faster than the read it replaces** (0.6 ms against 2.3 ms), and it
   takes nothing from the 20 server connections.
2. **A miss costs about twice a plain read** (p50 ≈ 4 ms in B once misses dominate): the
   database read plus the version, the lock, a second look, the store and the release. A
   cache that mostly misses is slower than no cache. In B that is from about one change per
   500 reads on.
3. **The hit ratio is decided by how the catalog is invalidated, not by Redis.** One version
   per workspace is one `INCR` and no race, and every change empties the workspace. Fine for
   a catalog that is edited a few times a day; a tenant that edits prices constantly would
   want a version per product (ADR 0010, rejected for now).
4. **Without protection a stampede is exactly as bad as it sounds**: 200 identical reads
   queue on 20 server connections, 348 ms for an answer that takes 2. Single-flight alone
   brings it to one read per process and is the fastest: the waiters are resolved by a
   promise. The lock brings it to one read in all; its waiters poll every 50 ms, which is the
   63 ms. With 4 processes the lock saves 3 reads; it earns its place with many replicas or
   an expensive load.
5. **Jitter is for another problem than the lock**: many keys dying together (after a deploy,
   after a bulk change), not many callers on one key.
6. **A cache makes replica lag last.** Without it a stale read heals in a millisecond; a
   cache would have kept it for five minutes for the whole workspace. A fill is a write, and
   reads the primary.

## Not measured

- The API under load with and without the cache: requests per second, and what the primary
  and PgBouncer gain. The numbers above are single reads from a script.
- Memory in Redis per tenant, and the keys of dead versions waiting for their TTL.
- Redis slow or down under load: the 500 ms command timeout on the request path.
- A lock holder dying mid-load (the 2 s wait of the others) under real traffic.
