# 2.4 Row-Level Security

Data: `pnpm db:datagen` (full), the same database as 2.2 and 2.3: 100 tenants, 2 M orders.
Postgres 18 in Docker on the same machine, defaults. Subject: the biggest tenant (467 506
orders) and a small one (2 950).

Reproduce: `pnpm db:explain:rls` (`services/api/prisma/explain/rls.sql`, full plans; psql as
the owner, then `SET ROLE oms_app`) and
`pnpm --filter @oms/api exec tsx prisma/explain/rls-frame.ts` (the client-side timing).

## What the application role sees

| Transaction                       | `SELECT count(*) FROM orders` (no filter) |
| --------------------------------- | ----------------------------------------- |
| no `app.workspace_id`             | **0**                                     |
| `set_config` to the big tenant    | 467 506                                   |
| `set_config` to the small tenant  | 2 950                                     |
| the next statement after `COMMIT` | **0**                                     |

## Plans

| #   | Query                                                | Plan                                                                                                            |
| --- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 0   | orders list, owner, explicit filter (as before 2.4)  | Index Scan `orders_workspace_id_created_at_id_idx`, `Index Cond: workspace_id = '…'`, 7 buffers                 |
| 2A  | the same as `oms_app`: explicit filter + policy      | the same Index Scan and Index Cond, 7 buffers, under a `One-Time Filter: current_setting(…)::uuid = '…'`        |
| 2B  | `oms_app`, filter removed: the policy alone          | the same Index Scan, `Index Cond: workspace_id = (NULLIF(current_setting('app.workspace_id', true), ''))::uuid` |
| 2C  | history of one order (partitioned, 2.3) as `oms_app` | 2 partitions scanned, 10 buffers, each under the same One-Time Filter                                           |

## The price of the frame

First page of the orders list, 2000 rounds on one connection, client and server on one host:

|                                                       | p50     | p95     |
| ----------------------------------------------------- | ------- | ------- |
| query alone (owner, no policy)                        | 0.39 ms | 0.64 ms |
| `BEGIN` + `set_config` + query + `COMMIT` (`oms_app`) | 1.18 ms | 1.71 ms |

In psql the three extra statements take 0.03 + 0.06 + 0.02 ms on the server.

## Findings

1. **The policy is an ordinary predicate for the planner.** `app_workspace_id()` is a `STABLE`
   SQL function, so it is inlined and its value is known when the executor starts: with the
   filter removed the policy itself becomes the `Index Cond` (2B). The indexes of 2.2 need no
   change, and partition pruning is untouched (2C).
2. **With both layers, the policy costs one comparison per query, not per row.** The
   application's own filter is the `Index Cond`; the policy turns into `setting = constant`,
   which Postgres checks once (`One-Time Filter`). If the two disagree, the scan does not start.
3. **Fail closed, silently for reads.** Without a tenant a `SELECT` returns zero rows and an
   `INSERT` fails with "new row violates row-level security policy". The silent half is why
   the extension still throws `TenantContextMissingError` first.
4. **The cost is round trips.** The server spends about 0.1 ms on the frame; the client waits
   three more round trips, about 0.8 ms here on one host and more over a real network. It is
   paid by every tenant query outside `@Transactional()`; inside one it is a single
   `set_config`.
5. **Removing the application filter keeps the isolation tests green.** With `scopeArgs`
   taken out of `tenant-scope.extension.ts`, 356 of the 357 int and e2e tests pass, the access
   matrix and the list tests (TEN-001…004, 008) among them: the database alone isolates. The
   one red test expects the extension's `TenantMismatchError` for a write that names another
   workspace and gets the policy violation of Postgres instead: still refused, with a worse
   error.

## Not measured

- Latency through the HTTP API, and over a network between the application and Postgres.
- The connection pool under load: every tenant read now holds a connection for four
  statements instead of one. Measured with PgBouncer in 2.7 (`docs/perf/2.7-pgbouncer.md`).
- Many policies or a join-heavy query, where a non-inlined policy would be a per-row cost.
