# 2.3 Partitioning `order_events`

Data: `pnpm db:datagen` (full): 7 681 703 order events over 24 months (2024-09-30 … 2026-09-29),
the same database as 2.2. Postgres 18, defaults (`shared_buffers=128MB`). Subject: the biggest
tenant and its order with the longest history (6 events, created 2024-09-30).

Reproduce: `pnpm db:explain:partitions` (`services/api/prisma/explain/partitions.sql`, full
plans). The "before" column was measured on the same data right before the migration.

## Results

| #   | Query                                             | Before (one table)                                          | After (29 monthly partitions)                                            |
| --- | ------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1A  | history by `order_id` alone                       | Index Scan, **5** buffers, 0.14 ms                          | Append over 29 Index Scans, **84** buffers, 0.65 ms                      |
| 1B  | history + the order's `created_at … updated_at`   | n/a                                                         | `Subplans Removed: 27`, 2 partitions, **7** buffers, 0.05 ms             |
| 1C  | 1B as a prepared statement, generic plan          | n/a                                                         | `Subplans Removed: 27` at execution, 7 buffers                           |
| 1D  | 1B with `enable_partition_pruning = off`          | n/a                                                         | 29 partitions again, 84 buffers                                          |
| 2A  | one tenant, one month (`count(*)`)                | Index Only Scan of the PK, **17 720** buffers, 2 974 ms     | Index Only Scan of one partition, **423** buffers, 67 ms                 |
| 3   | retention by `DELETE` of one month (90–98 k rows) | Seq Scan of the table, 261 217 buffers, 353 ms, 24.9 MB WAL | Seq Scan of one partition, 59 ms, 20.2 MB WAL; the partition stays 34 MB |
| 4   | retention by `DROP` of one partition (37 MB)      | not possible                                                | **16 ms**, the files are gone                                            |

2A and 3 took different months before and after (March 2025 and November 2024 before,
October 2024 after): compare the shape and the order of magnitude, not the exact numbers.

Planning time: 0.5 ms before, 2.4 ms for 1A (29 partitions to plan), 1.0 ms for 1B.

Sizes:

|                                                        | Before  | After (sum) | Largest partition |
| ------------------------------------------------------ | ------- | ----------- | ----------------- |
| heap                                                   | 1253 MB | 1252 MB     | 113 MB            |
| `order_events_workspace_id_order_id_created_at_id_idx` | 1018 MB | 1009 MB     | 91 MB             |
| `order_events_pkey`                                    | 655 MB  | 653 MB      | 58 MB             |

The migration itself (rename, create, copy 7.7 M rows, drop) took 1 min 57 s.

## Findings

1. **Partitioning does not make a lookup faster; it can make it slower.** `order_id` says
   nothing about `created_at`, so the planner probes the index of every partition: 84 pages
   instead of 5 (1A). The partition key has to be in the query. An order's events lie between
   its `created_at` and `updated_at` (the domain stamps both with the same `now`), so
   `OrdersQueryService.listEvents` sends that range and the scan touches the two months the
   order lived in (1B). The app's queries are parameterized: pruning then happens when the
   executor starts (1C), still before any partition is read.
2. **A time-range query is where pruning pays.** One month of one tenant read 17 720 pages of
   the primary key (`workspace_id, id, created_at`: every entry of the tenant, filtered by
   time); with partitions it reads one month's primary key, 423 pages (2A).
3. **DROP instead of DELETE.** `DELETE` writes every row to the WAL (20 MB for 90 k rows) and
   marks it dead; heap and indexes keep their size until VACUUM, and the file does not shrink
   after it either. `DROP` of a partition is a catalog change plus file removal: 16 ms, and
   37 MB returned to the OS. On the unpartitioned table the `DELETE` also had to scan all
   1.2 GB to find the month.
4. **The total size did not change, and the 2.2 guess was wrong.** 2.2 suspected page splits
   behind the 1018 MB index. Rebuilt from scratch per partition it is 1009 MB: the index is
   simply that large (four key columns, 7.7 M rows). What changed is the working set: inserts
   go to the current month's indexes (91 MB + 58 MB at the busiest month), not to two indexes
   of 1.7 GB.
5. **Cost.** More planning time per query, 29 tables to vacuum and analyze, a job that must
   keep running, and a write error if it does not. Worth it for a table that only grows and
   has a retention or archiving story; not for a table that is read by key only.

## Not measured

- Insert throughput before and after (the working-set argument in finding 4 is reasoning, not
  a benchmark).
- `DETACH … CONCURRENTLY` under write load; block 4 times a plain `DROP` in a transaction.
- WAL written by the `DROP` (psql `\timing` only).
