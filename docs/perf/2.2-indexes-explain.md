# 2.2 Indexes and EXPLAIN

Data: `pnpm db:datagen` (full): 2 M orders, 7.7 M order events, 5 M order items.
Postgres 18, defaults (`shared_buffers=128MB`, `work_mem=4MB`): the working set does not fit
in the cache, so plans show `read=`. Subject: the biggest tenant (467 506 orders; FULFILLED
408 621, PAID 2 587) and a keyset position 100 000 rows deep (≈ page 5000).

Reproduce: `pnpm db:explain` (`services/api/prisma/explain/lists.sql`, full plans).

## Findings

1. **The OR cursor was a hidden OFFSET.** Prisma cannot express the conventions'
   `(created_at, id) < ($1, $2)` (`read/query-service.md` §4), so `afterCursor` used
   `created_at < c OR (created_at = c AND id < i)`. B-tree cannot start a scan from an OR: the
   index gave the order, but the scan began at the newest row and discarded everything before
   the cursor (1B ≈ 1E, linear in depth). Fix: a redundant `created_at <= c` (`>=` for the
   ascending list) that Postgres uses as Index Cond; the OR only breaks ties (1C).
   `$queryRaw` with the row comparison would be faster still (1D) but bypasses the tenant
   extension. One helper (`shared/pagination/cursor.ts`) fixes orders, events, products,
   members and "my workspaces".
2. **Index choice follows selectivity.** For a rare status the status index is exact (2A). For
   a status that is 87 % of the tenant the planner walks the index without status and filters:
   1 373 rows removed to find 21 is cheaper than the status index (2B). Both are right.
3. **Without the list indexes** every list is a parallel Seq Scan of the whole table plus a
   Sort (5A/5B): 55 000 pages for 21 rows, regardless of the tenant's size.
4. **Bitmap is for "many rows, no order"** (4B): it reads each heap page once in physical
   order, and loses the index order.
5. **Index Only Scan** needs a fresh visibility map: `Heap Fetches: 0` after datagen's
   `VACUUM ANALYZE` (3A, 4A).
6. **Sizes.** `order_events_workspace_id_order_id_created_at_id_idx` is 1018 MB, larger than
   the primary key (655 MB). Likely page splits: events are appended in time order but the
   index is keyed by order, so inserts land all over it (not verified; a REINDEX would show). Watch it in 2.3 (partitioning splits it per month).
   `order_items_workspace_id_{order,product}_id_idx` show `idx_scan = 0`: they serve FK checks
   and cascades, not reads.

## Deep history pages

Datagen orders have at most 6 events, so the history cursor never goes deep here: the fix
for `afterCursorAsc` is preventive.
