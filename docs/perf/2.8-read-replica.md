# 2.8 Read replica and read-your-writes

Data: `pnpm db:datagen` (full), the same database as 2.2–2.7: 100 tenants, 2 M orders, 5.5 GB.
Postgres 18 primary and one asynchronous streaming standby (`postgres-replica`,
`hot_standby_feedback = on`, no replication slot) in Docker on one machine; the application
reaches both through PgBouncer. Decision and rejected alternatives: ADR 0009.

Reproduce A–D: `pnpm db:explain:replica` (`services/api/prisma/explain/replica.ts`). It writes
no row: a commit is made with `pg_logical_emit_message`, a WAL record without data. E and F
were run by hand against the API with `DATABASE_REPLICA_URL` set. The numbers are one run on a
laptop; the first copy of the primary (`pg_basebackup`, 5.5 GB) took about 20 s.

## A. Replication state

| Where   | What it reports                                                              |
| ------- | ---------------------------------------------------------------------------- |
| primary | `pg_stat_replication`: `walreceiver`, `streaming`, `async`, `replay_lag` ≈ 0 |
| replica | `pg_is_in_recovery() = true`, the same replay position as the primary sent   |

## B. Replication lag at rest

From a commit on the primary until `pg_last_wal_replay_lsn()` on the replica has passed it,
300 commits, one at a time. The position is polled, so one round trip (about 1 ms) is the
resolution: the lag is at most what is shown.

| p50     | p95     | max      |
| ------- | ------- | -------- |
| 0.94 ms | 1.94 ms | 10.07 ms |

## C. The same read on both servers

The first page of the orders list of the biggest tenant (467 506 orders), in the tenant frame
of 2.4 (`BEGIN; set_config; query; COMMIT`), as the application role, 300 rounds:

|         | p50     | p95     |
| ------- | ------- | ------- |
| primary | 3.78 ms | 7.62 ms |
| replica | 4.44 ms | 8.43 ms |

As the application role with no tenant set, the replica shows 0 of the 2 M orders: the
Row-Level Security policies came with the copy.

## D. The position check, with a replica 5 s behind

`recovery_min_apply_delay = '5s'` on the replica: it receives the WAL at once and applies it
five seconds later. The check is the one `ReadYourWrites` runs before a `GET` of a user who
wrote lately: `pg_last_wal_replay_lsn() >= <position stored after the write>`.

| Moment                 | The check | The writer's next `GET` reads |
| ---------------------- | --------- | ----------------------------- |
| right after the commit | `false`   | the primary                   |
| 4.99 s later           | `true`    | the replica again             |

The check itself, one round trip to the replica: p50 1.10 ms, p95 2.38 ms.

## E. Through the API: create an order, then read

The same 5 s delay. `member@acme.test` creates an order (`POST /orders`), then both that user
and a colleague (`admin@acme.test`) read the list and the order:

| After the `POST` | The writer: list / order | The colleague: list / order |
| ---------------- | ------------------------ | --------------------------- |
| 0.2 s            | there / 200              | **missing / 404**           |
| 2 s              | there / 200              | missing / 404               |
| 4 s              | there / 200              | missing / 404               |
| 6 s              | there / 200              | there / 200                 |

## F. The replica stopped

`docker compose stop postgres-replica`, the API left running:

| Request                                   | Result                                |
| ----------------------------------------- | ------------------------------------- |
| `POST /orders`                            | 201                                   |
| `GET /orders` of the user who just wrote  | 200, from the primary, with a warning |
| `GET /orders` of a user who wrote nothing | **500**                               |

After `docker compose start postgres-replica` it was streaming again by itself. The first read
routed to it afterwards still failed once: PgBouncer keeps a failed server login for
`server_login_retry` (15 s) and answers the next client with it before it tries again.

## Findings

1. **At rest the replica is about a millisecond behind**, and a read costs the same on it as
   on the primary. The lag is invisible until something makes the replica slow: load, a long
   query that holds back replay, a network. With 5 s of it, a colleague does not see a new
   order for 5 s, and its address answers 404.
2. **The writer never notices.** After a mutating request the primary's WAL position is kept
   for that user, and their reads stay on the primary exactly until the replica has replayed
   it: 5 s here, a millisecond at rest. No fixed "stick to the primary for N seconds" was
   needed, and a generous TTL (60 s) costs nothing once the replica caught up.
3. **The request decides, not the query.** `GET` may read the replica; a mutating request and
   the worker read the primary, so a price or a tax rate that is copied into an order is
   never a stale one. The query services did not change.
4. **The price of read-your-writes** is one Redis `GET` per `GET` request, plus one round trip
   to the replica (about 1 ms here) while the caller has a marker.
5. **Row-Level Security needed nothing on the replica**: physical replication copies roles,
   grants and policies, and `set_config` is allowed in a read-only transaction.
   `@prisma/extension-read-replicas` could not be used for the same reason the tenant frame
   exists: it sends everything inside a transaction to the primary.
6. **A replica is one more thing that can be down.** Without it the reads of users who wrote
   nothing lately fail; a user with a marker falls back to the primary. Health checks and
   failover are Step 4.

## Not measured

- The primary under read load with and without the replica: how much the replica takes off it.
- Lag under write load, and with a long query on the replica holding back replay.
- A recovery conflict: a query on the replica cancelled by replay.
- More than one replica: a user could read a fresher one first and a staler one next.
