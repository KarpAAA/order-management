# 2.7 PgBouncer in transaction mode

Data: `pnpm db:datagen` (full), the same database as 2.2–2.4: 100 tenants, 2 M orders.
Postgres 18 (`max_connections = 100`) and PgBouncer 1.25 (`max_client_conn = 500`,
`default_pool_size = 20`) in Docker on one machine. Subject: the first page of the orders list
of the biggest tenant (467 506 orders), sent as the application sends it since 2.4:
`BEGIN; set_config('app.workspace_id', …, true); query; COMMIT`.

Reproduce: `pnpm db:explain:pgbouncer` (`services/api/prisma/explain/pgbouncer.ts`). One Node
process drives every client, so the transactions per second below are what that process can
send, not what Postgres can take. The numbers are one run; between runs on this machine the
throughput moved by about 20 %, the counts of connections not at all.

## A. The price of the hop

One connection, 2000 rounds:

|                    | p50     | p95     |
| ------------------ | ------- | ------- |
| direct to Postgres | 1.28 ms | 2.28 ms |
| through PgBouncer  | 1.50 ms | 2.29 ms |

## B. Many clients on few server connections

Every client repeats the transaction for 10 s. Peaks sampled every 250 ms from `SHOW POOLS`
and `pg_stat_activity` (`open`: Postgres processes of `oms_app`; `busy`: those in a transaction).

| Clients               | tx/s | p50      | p95      | p99      | Processes open / busy | `cl_active` / `cl_waiting` | `sv_active` |
| --------------------- | ---- | -------- | -------- | -------- | --------------------- | -------------------------- | ----------- |
| 499 through PgBouncer | 3067 | 152.5 ms | 219.1 ms | 382.2 ms | **20** / 20           | 29 / 479                   | 20          |
| 20 direct             | 3618 | 5.1 ms   | 9.3 ms   | 13.7 ms  | 40 / 20               |                            |             |
| 75 direct             | 2927 | 23.0 ms  | 51.9 ms  | 82.5 ms  | 95 / 70               |                            |             |

The direct rows count the 20 idle server connections PgBouncer keeps open: 40 = 20 + 20.
The third run asked for 90 connections and got 75.

## C. The two limits

| 500 clients                                 | Connected | Refused | Error                                                                            |
| ------------------------------------------- | --------- | ------- | -------------------------------------------------------------------------------- |
| through PgBouncer (the console is one more) | 499       | 1       | `no more connections allowed (max_client_conn)`                                  |
| direct to Postgres                          | 76        | 424     | `remaining connection slots are reserved for roles with the SUPERUSER attribute` |

## D. A setting on a shared server connection

Two clients of PgBouncer. The first sets the tenant, the second sets nothing and runs
`SELECT count(*) FROM orders`:

| The first client ran                          | The second client, on the same backend, counts |
| --------------------------------------------- | ---------------------------------------------- |
| `set_config(…, true)` inside `BEGIN … COMMIT` | **0**                                          |
| `set_config(…, false)` (session-level)        | **467 506**: the first client's tenant         |
| (the owner then closes that backend)          | 0, on a new backend                            |

## Findings

1. **500 client connections are 20 Postgres processes.** Under load every one of the 20 is
   busy and 479 clients wait in line; nobody is refused and nothing fails. Postgres itself
   takes 76 of the same 500 and refuses the rest.
2. **Fewer server connections are not slower.** 20 connections carried as many transactions
   per second as 75 did (the client process is the limit in all three runs). What grows with
   the number of clients is the time each one waits for its turn: 150 ms at 499 clients on 20
   connections, which is the queue, not the query.
3. **The limits fail differently.** Past `max_client_conn` a client is refused at once. Inside
   it, with every server connection busy, a client waits (up to `query_wait_timeout`, 120 s
   by default).
4. **The hop costs about 0.2 ms per transaction** of four statements here, on one host.
5. **A session-level setting is a cross-tenant leak behind a pooler.** PgBouncer hands the
   server connection to the next client as it is; in transaction mode nothing resets it. With
   `is_local = true` the setting is gone at `COMMIT`, before the connection returns to the
   pool: the reason for that choice in 2.4 (ADR 0006).
6. **No Prisma setting was needed.** `@prisma/adapter-pg` sends unnamed prepared statements
   unless a `statementNameGenerator` is given; the old `pgbouncer=true` flag has no meaning
   with a driver adapter. One int test file runs the application's database layer through a
   PgBouncer (`test/tenancy/pgbouncer.int-spec.ts`, TEN-013); the rest of the suite still
   connects to Postgres directly.
7. **PgBouncer's own connections count against `max_connections`.** Its 20 idle server
   connections are why only 76 direct clients fit, not 97.

## Not measured

- Latency through the HTTP API, and with a network between the application, PgBouncer and
  Postgres.
- A load that Postgres, not the client process, limits: the pool size at which throughput
  peaks on this machine.
- Long transactions: one that holds its server connection for seconds takes a twentieth of
  the pool with it.
