# 0006 — Row-Level Security and a non-owner application role

Date: 2026-10-01 Status: accepted

## Context

Tenant isolation lived in one Prisma client extension (ADR 0002). Anything that went around
it (raw SQL, the unscoped client, a nested write through a global model) reached every
tenant, and the application connected as the superuser that owns the tables. Step 2.4 moves
the rule into Postgres, as the first of three tenancy modes (shared tables with RLS).

## Decision

- **Two roles.** The owner (`oms`) runs migrations, seed and datagen through
  `DATABASE_ADMIN_URL`. The api and the worker connect as `oms_app` through `DATABASE_URL`:
  no ownership, no `BYPASSRLS`, DML on the seven tables and nothing else. The migration creates
  the role without a login; the login is set by the environment (`devtools/postgres/init`, the
  test setup). `DATABASE_ADMIN_URL` is not in the application's env schema.
- **Policies.** Every tenant table has `tenant_isolation`:
  `workspace_id = app_workspace_id()` for `USING` and `WITH CHECK`, where the function reads
  the transaction-local setting `app.workspace_id`. `ENABLE`, not `FORCE`: the owner must see
  every tenant for backfills, and the application is never the owner.
- **The setting is transaction-local** (`set_config(…, true)`): a pooled connection, and later
  PgBouncer in transaction mode (2.7), never carries a tenant to the next query. So every
  tenant query runs in a transaction. `@Transactional()` sets it as its first statement
  (`transactional.adapter.ts`); a query outside one is wrapped by the tenant extension in
  `BEGIN; set_config; query; COMMIT`. Both live in `infrastructure/database/`.
- **Both layers stay.** The extension still adds `workspace_id` and checks writes: it gives
  `TenantContextMissingError` / `TenantMismatchError` instead of an empty list or a Postgres
  error, and the explicit filter keeps the plans of 2.2 as they were.
- **A user's own memberships** are readable across workspaces through a second policy,
  `own_memberships FOR SELECT USING (user_id = app_user_id())`, set by
  `PrismaService.asUser`: the access guard's lookup, `/me`, "my workspaces". Writes to
  `memberships` stay bound to the tenant, so creating a workspace runs its transaction as the
  new workspace (the id is generated by the application).
- **Partition maintenance** goes through two `SECURITY DEFINER` functions the role may only
  execute. A function runs in a transaction, so `DETACH … CONCURRENTLY` is gone: the drop is a
  plain `DROP TABLE` under `lock_timeout = 5s`; the job retries on its next run. This replaces
  the "separate owner connection" that ADR 0005 expected.
- **Partitions carry no grant.** `oms_app` reaches them only through `order_events`, where the
  policy applies; hence no `ALTER DEFAULT PRIVILEGES`, and every new table needs its own
  `GRANT` and policy in its migration. `test/tenancy/row-level-security.int-spec.ts` fails for
  a table with `workspace_id` and no policy, or a table without a grant.
- Rejected: a `BYPASSRLS` connection for the cross-tenant reads (the bypass would live in the
  process again); a session-level `SET` (leaks through the pool); `@Transactional()` on every
  query service (changes every module, and a forgotten one returns an empty list).

## Consequences

- A bug that bypasses the extension returns nothing instead of another tenant's rows.
- Every tenant query outside `@Transactional()` costs three more round trips
  (`docs/perf/2.4-rls.md`). The N+1 guard of the e2e suite counts data statements only.
- The root scoped client used while a transaction is open runs in a transaction of its own,
  on another connection: it does not see the open transaction's writes. The extension tells
  the two apart through Prisma's `__internalParams.transaction`, which is not public API; an
  int test fails if an upgrade drops it.
- The tenant must be bound before a transaction begins. Bound later, it is not applied and the
  database stays closed.
- Local dev needs the role's login: a fresh volume gets it from the init script, an existing
  one from one `ALTER ROLE` (README).
- `migrate diff` sees no role, grant, policy or function: the int tests are their only guard.
